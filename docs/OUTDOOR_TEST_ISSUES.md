# 실외 시험에서 드러난 문제 정리

작성 2026-09-01. 메인봇(Jetson Orin) + 팔로워봇(Raspberry Pi) 화재 대응
연동을 실내에서 실외로 옮기는 과정에서 나온 것들이다.

시험 구성

    지도     argos_outdoor_imu_v1   561 x 464 @ 0.05 m  (약 28 x 23 m)
    메인봇   순찰 + YOLO/MLP 인지 + 화재 접근 + 좌표 송신
    팔로워   좌표 수신 -> Nav2 자율주행 -> 살수(현재 dry-run) -> 복귀
    통신     ROS 2 Jazzy, ROS_DOMAIN_ID=42, 같은 무선망

## 아직 안 고친 것

### 1. 실외에서 위치 추정이 불안정하다  ← 오늘의 최대 문제

같은 자리에 세워 둔 로봇을 스캔 정합으로 찾을 때마다 다른 답이 나온다.

    메인봇   1차 탐색      (+6.81, +0.22)   적합률 90.5%  벽뚫음 0.0%
             AMCL 이 간 곳 (+10.80, -1.86)  <- 벽에 박혀 정지
             2차 탐색      (+0.45, -0.14)   적합률 83.0%  벽뚫음 0.0%

    팔로워   전역 탐색     (-0.19, -0.10)   적합률 81.2%  벽뚫음 0.8%
             메인 주변 1.3m (+8.03, +0.44)  적합률 67.6%  벽뚫음 1.5%
             메인 주변 2.0m (+7.20, +0.14)  적합률 64.9%  벽뚫음 0.0%
             라이다 역산   (+5.97, +0.65)   적합률 52.2%  벽뚫음 10.3%

11 m 넘게 벌어지는데 어느 쪽도 "벽을 뚫고 본 빔" 기준으로는 합격이다.

원인으로 보이는 것

  - 유효빔이 적다. 팔로워 LD08 은 450 빔 중 **133~145 개**만 유효했다.
    실외는 반사할 벽이 적어 대부분의 빔이 무한대로 돌아온다.
  - 지도에 없는 물체가 많다. 가려짐이 **31~37%** 다. 8/29 에 만든 지도라
    그 뒤에 놓인 물건, 주차 차량, 사람이 전부 미지 물체로 잡힌다.
  - 그 결과 180도 모호성이 생긴다. 탐색 범위를 바꿀 때마다
    yaw 187도 <-> yaw 5도 를 오갔다.

결국 팔로워 자세는 사용자가 알려준 "메인봇 뒤쪽, 같은 방향" 이라는
정보로 후보를 하나만 남겨서 확정했다. 자동화된 방법으로는 못 골랐다.

해볼 만한 것

  - 실외 지도를 다시 만든다. 지금 물건 배치 그대로 SLAM 을 돌린다.
  - 시험 구역을 벽/구조물이 있는 쪽으로 좁힌다. 트인 공간에서는
    라이다 정합 자체가 성립하지 않는다.
  - 초기 자세를 사람이 지정한다. 실외에서는 이게 가장 확실하다.

### 2. 팔로워가 불 좌표 18 cm 까지 붙는다

`arrival_radius_m: 0.18` 이다. 메인봇은 불에서 0.60 m 에 멈추는데
팔로워는 불 위로 올라간다. 실제로 물을 쏠 때 노즐 사거리에 맞는
이격 거리가 필요하다. 접근 방향 기준으로 목표를 뒤로 물리면 된다.

### 3. MLP 입력 8개 중 2개가 죽어 있다

IR 온도가 계속 0.0 으로 들어온다. 전체 로그 기준 0.0 이 3337 회,
0 이 아닌 값이 314 회(8.6%) 였고, 나중에는 12 초 182 프레임이 전부 0 이었다.

    MLP 특징 = fire_conf, smoke_conf, cigarette_conf, spark_conf,
               temperature, gas, temp_change, gas_change

`temperature` 와 `temp_change` 가 상수 0 이면 학습 때 분포와 달라진다.
YOLO 감지가 하나도 없는 상태에서 mlp_prob 이 0.465 까지 올라갔다.
임계값 0.70 에는 못 미쳤지만 가스 단독으로 그만큼 오른 것이다.
아두이노 IR 센서가 원래 열원 없으면 0 을 내는 방식인지 확인이 필요하다.

### 4. `/map` 이 Pi 로 느리게 간다

실외 지도는 561 x 464 = **254 KiB** 인데 Pi 의 UDP 수신 버퍼
(`net.core.rmem_max`) 는 **208 KiB** 다. 메시지 하나가 버퍼보다 커서
조각이 유실되고 재전송으로 결국 도착하지만 15 초를 넘긴다.
실내 지도는 12 KiB 라 문제가 없었다.

지금은 자세 탐색 도구의 대기 시간을 90 초로 늘려 넘겼다. 근본 해결은
둘 중 하나다.

  - `net.core.rmem_max` 를 키운다 (sudo 필요, Pi 는 비밀번호를 묻는다)
  - Pi 에서 자체 map_server 를 띄워 지도를 로컬로 읽는다 (네트워크 전송 없음)

## 오늘 고친 것

### 5. 순찰이 갇혀서 못 움직였다

`select_patrol_target()` 이 표본을 뽑기 **전에** 로봇 자신의 자리를
검사하고, 0.35 m 원판에 미지(-1) 나 점유 셀이 하나라도 있으면 즉시
`None` 을 반환했다.

    검사식  np.all((values >= 0) & (values <= free_max))   <- 미지 -1 은 탈락

빠져나갈 수 없는 상태다. 제 자리가 위험하다고 판단해서 안 움직이는데,
안 움직이니 영원히 그 자리다. 실제로 순찰 목표 4 개를 소화한 뒤
원판에 미지 7 · 점유 13 셀이 걸려 **151 회 연속** 실패하며 멈춰 섰다.

로봇은 이미 물리적으로 거기 있으므로 나가는 길을 찾는 것이 맞다.
시작 지점 하드 실패를 없애고 지도 경계 검사만 남겼다. 목표점 쪽
검사는 그대로 엄격해서 위험한 곳으로 보내지는 않는다.

  파일  scripts/fire_nav_integrated.py  `select_patrol_target()`
  검증  더러운 원판에서 40/40 성공, 주변이 전부 미지면 여전히 None,
        지도 밖 자세도 여전히 None

### 6. 팔로워가 임무를 마치고 돌아오지 않았다

상태기계가 `NAVIGATING -> SETTLING -> SPRAYING -> COMPLETE` 에서 끝나고
COMPLETE 에서는 정지 명령만 냈다. 팔로워가 불이 있던 자리에 계속 서
있었고, 순찰을 재개한 메인봇이 그 근처를 지나가며 부딪쳤다.

실내 시험 기록

    메인봇 위치     (+0.31, -0.05)
    전달된 불 좌표  (+0.02, +0.09)   <- 메인봇에서 0.32 m
    팔로워 목표     정확히 그 지점

`RETURNING` 상태를 넣었다. 지령을 받은 순간의 자세를 `home` 으로
기억했다가 살수가 끝나면 그 자리로 돌아가고 도착하면 COMPLETE 다.
복귀도 Nav2 가 몬다 (내장 점 제어기는 직선으로만 가서 왔던 길에
장애물이 생기면 밀고 들어간다).

  파일  follower: mission.py, fire_supervisor_node.py, config/follower_fire.yaml
  설정  return_home: true, home_arrival_radius_m: 0.30, return_timeout_s: 120.0

### 7. 도착해 놓고 실패했다

`SETTLING` 에 자세 유예가 없어서 자세가 0.5 초만 낡아도 즉시
`_fail("localization lost while confirming stop")` 이었다. 막 멈춘
직후는 AMCL 갱신이 뜸해지는 구간이라 실패하기 딱 좋은 자리다.
`NAVIGATING` 과 같은 1.0 초 유예를 줬다.

### 8. 장애물 게이트가 임무를 죽였다

감독기의 LiDAR 장애물 게이트가 앞 0.45 m 안에 뭔가 10 초 이상 있으면
`_fail("obstacle persisted")` 로 임무를 통째로 취소했다. 이 게이트가
내는 정지 명령은 Nav2 주행 중에는 이미 무시되고 있어서, **임무를
죽이는 권한만 남아 있었다.** 메인봇이 팔로워 진행 방향에 서 있으면
정확히 이게 걸린다.

Nav2 주행 중에는 회피를 코스트맵에 맡기도록 껐다. 정말 못 가면 Nav2 가
목표를 실패시키고 그건 별도로 보고된다.

### 9. 감독기가 로깅으로 죽었다

    log = self.get_logger().info if accepted else self.get_logger().error
    log(reason)          # <- 같은 줄에서 심각도가 바뀐다

rclpy 는 (파일, 함수, 줄) 로 로그 위치를 캐싱해서 같은 줄에 다른
심각도를 쓰면 `ValueError: Logger severity cannot be changed between
calls.` 로 죽는다. 지금까지 전부 "수락" 만 나와서 안 터졌던 것이고,
**디스패치가 한 번이라도 거절되면 화재 대응 도중 감독기가 내려간다.**
`_on_dispatch` / `_on_cancel` / `_on_reset` 세 군데 호출 지점을 나눴다.

### 10. 팔로워 Nav2 가 메인봇을 몰았다

두 로봇의 Nav2 가 같은 이름과 같은 토픽을 썼다. 특히 팔로워
`controller_server` 가 `/cmd_vel` 로 내면 메인봇 `argos_base_driver` 가
그걸 받아 **메인봇이 움직였다.**

팔로워 Nav2 전체를 `/follower` 네임스페이스로 옮겼다. 그 과정에서
딸려 나온 것 둘.

  - `static_layer` 의 상대 토픽 `map` 이 `/follower/map` 으로 풀려
    글로벌 코스트맵이 지도를 못 받았다. 플래너가 로봇을 (0,0) 으로
    보고 경로를 못 만들었다. yaml 에 `map_topic: /map` 을 박았다.
  - `default_server_timeout: 20` ms 라 BT 가 플래너 응답을 42 ms 만에
    포기했다. 500 ms + `wait_for_service_timeout: 5000` 으로 올렸다.

### 11. cmd_vel_bridge 가 3 개 떠 있었다

Nav2 를 재기동할 때마다 브리지가 하나씩 남아서 셋이 같은 모터에 명령을
밀어넣고 있었다. 1 개로 정리했다. **launch 를 죽여도 자식 노드는 살아
남는다** -- 정리할 때 자식까지 확인해야 한다.

### 12. 스파크/담배 알림 기준 추가

원본 `new_main_robot_map.py` 에는 클래스별 알림 기준이 없고 MLP 확률
하나(>= 0.70)로만 알림을 냈다. 스파크와 담배꽁초는 오탐이 잦아서 약한
신뢰도로 알림이 나가면 사용자가 알림을 무시하게 된다.

원본은 건드리지 않고 래퍼의 알림 게이트에 클래스 판정을 넣었다.
막는 범위는 좁게 잡았다.

    스파크 0.30 만                차단
    담배 0.40 만                  차단
    스파크 0.30 + 담배 0.40       차단
    스파크 0.50 (경계)            통과
    약한 스파크 + 불              통과
    YOLO 무감지 (가스/온도 단독)  통과   <- 카메라에 안 잡히는 화재를 놓치지 않는다

  파일  scripts/fire_perception_main.py
  설정  alert_conf_spark: 0.5, alert_conf_cigarette_butt: 0.5 (런타임 조정 가능)

주의: 이 게이트는 **알림만** 막는다. 주행 쪽 접근 판단은 따로
`approach_conf_cigarette_butt=0.55`, `approach_conf_spark=0.70` 을 쓴다.
담배 0.52 면 접근은 안 하지만 알림은 나간다.

## 도구에 넣은 것

### 자세 탐색 범위 제한

실외에서 전역 탐색이 헐겁게 걸려 실제와 7 m 떨어진 자리를 "적합률
81%" 로 내놓는다. 다른 로봇의 라이다로 대략 위치를 알 수 있으면 그
근방만 보게 한다.

    scan_map_search.py --near-x 6.811 --near-y 0.223 --near-radius 1.3

지도 대기 시간도 15 초에서 90 초로 늘렸다 (위 4번 항목).

### MLP 실시간 대시보드

    python3 ~/argos_project/scripts/mlp_dashboard.py
    -> http://192.168.0.18:8088

`mlp_prob` 과 임계값 0.70, 최근 200 프레임 추이, MLP 입력 8 개 전부,
텔레그램 상태를 15 Hz 로 보여준다. `temp_change` / `gas_change` 는
토픽에 안 실려서 원본과 같은 2 초 창으로 다시 계산한다 -- 판정 자체는
원본이 낸 `mlp_prob` 을 그대로 쓴다.

## 되풀이해서 나온 실수 (내 쪽)

  - `pkill -f "패턴"` 이 내 셸 명령줄 자체를 잡아 세션을 죽였다.
    브래킷 트릭(`[p]attern`)을 써도 같은 명령줄 뒤쪽에 그 문자열이
    다시 나오면 소용없다. 죽이는 단계와 띄우는 단계를 분리해야 한다.
  - 도메인을 안 맞췄다. 실제 스택은 `ROS_DOMAIN_ID=42` 인데 새 셸은
    0 이라 노드가 하나도 안 보였다.
  - `ros2 topic pub -1` 단발 발행이 discovery 경쟁에서 져서 메시지가
    유실됐다. 손으로 쏠 때는 `-r 1 -t 3` 을 쓴다.
  - `argos_env.sh` 를 안 쓰고 워크스페이스를 직접 source 해서
    `ydlidar_ros2_driver` 를 못 찾았다.
